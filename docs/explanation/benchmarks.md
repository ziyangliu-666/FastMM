# Benchmarks

Results: [`bench/README.md`](../../bench/README.md), generated by `scripts/bench.sh`; its end-to-end section comes from `scripts/bench-e2e.sh`. Across two hosts: `scripts/bench-2host.sh` ([Two-host benchmark](../how-to/operations/two-host-benchmark.md)).

## Method

- `scripts/bench.sh --preset release-native --cpu 2` runs each benchmark binary twice. The first pass is pinned to one core (`taskset` plus `sched_setaffinity` in the bench main) and skips the benchmarks the binary declares as needing more than one core; the second runs exactly those, unpinned. A benchmark declares the requirement in its own source with `FASTMM_BENCH_NEEDS_CORES` (`bench/bench_pin.hpp`), the binary prints the list for `--fastmm-multicore-filter`, and a benchmark that finds fewer cores in its affinity mask than it asked for fails instead of reporting a number. `BM_ReactorEchoThread` pinned with its echo thread on the same core measured a busy-polling round trip at 8.4 ms against 11.0 µs unpinned.
- Five repetitions per benchmark, reported raw, and `--rounds N` repeats the whole suite; `tools/bench_table.py` pools them. Per benchmark it publishes the fastest repetition (interference only makes a benchmark slower, so on a shared machine that is the least disturbed estimate), the process CPU time of that same repetition, and the median and full range over every repetition of every round. Google Benchmark's `stddev` aggregate (the standard deviation of five repetition means) is not published.
- Per-operation percentiles exist only where a benchmark times every operation itself with `rdtsc` into a `LogLinearHistogram` and exports `p50`/`p99` (reactor, UDP, tick-to-order) or `p50_ns`/`p99_ns` (codecs). Everywhere else Google Benchmark reports one mean per repetition and there is no per-operation distribution to publish.
- `BM_TickToOrder_Sim` measures the engine inside the simulator: a book delta into the feed, `Engine::step()`, and the orders serialised into `SimTransport`, whose `send()` copies each message into a 192-byte scheduler slot and pushes it on the arrival heap (the simulator's stand-in for the live engine's outbound ring push). TLS, JSON decoding and the network are outside it. The simulator's outbound SHA-256, a determinism check rather than engine work, is off for this benchmark (`SimTransportConfig::hash_outbound`); `BM_TickToOrder_SimHash` is the same run with it on, and the difference is what it costs.
- Between timed ticks the rig runs the simulated venue and delivers acks, untimed, until no order is in flight and both quotes rest at the venue. The quote manager does not touch a pending order, so a tick that finds one sends nothing. Each timed tick moves the book by two ticks and sends one cancel per side. The benchmark reports `order_events_pct`, the share of ticks that sent orders, and fails when it is below 50 %. Timing is manual (`UseManualTime`): the reported time is the `rdtsc` interval around the tick and nothing else. `PauseTiming`/`ResumeTiming` around the settle loop would add about 600 ns to a roughly 300 ns operation.
- The codec benchmarks time 64 operations between two `rdtsc` readings and report the median per-operation time as `p50_ns`; their Google Benchmark time is per batch, that is, 64 times larger. A benchmark that repeats one input lets the compiler hoist work out of the loop (`BM_Ouch42_EncodeEnterOrder`); the `*_NewIds` variants change the ClOrdID every call. `BM_Ouch50_EncodeColdMap` builds a fresh `UserRefMap` before each batch, so it shows what the first orders of a session pay; run it with `MALLOC_MMAP_THRESHOLD_=65536` when comparing against a build whose tables come from `malloc`, which otherwise hands back pages already faulted in by the previous batch.
- Benchmark loops that carry no dependency from one iteration to the next measure throughput. `BM_Risk_CheckNew_Pass`, `BM_Fixed_Mul`, `BM_Fixed_RoundToTick` and `BM_L2_UpdateNearTop` now chain the result into the next iteration's input, so they measure the latency of one operation; `BM_Risk_CheckNew_Killed`, `BM_Fixed_FromDecimal`, `BM_Fixed_ToDecimal` and `BM_L2_InsertEraseTop` remain throughput and say so in their source.
- `BM_ItchL2Bridge_Message_LargeBook` replays a stream that keeps 200,000 to 260,000 orders resting, so the 2^20-order book's reference index (2^21 slots, 32 MiB) and its order pool are touched: 81.9 ns per message against 57.3 ns for the small book. `BM_ItchL2Bridge_Message_LargeBookSmallSet` configures the large book but replays the small stream (2,000 to 6,000 live orders, 61.4 ns), so the difference is the working set rather than the capacity. The price spread stays at about 300 levels in all three: the benchmark varies the number of resting orders, not the number of levels.
- Profiles: `perf` from the distribution's `linux-tools` package works unprivileged under WSL2 (`kernel.perf_event_paranoid = 2`, user-space cycles and cache events; no LBR). Unpack it with `apt-get download` and `dpkg -x` when it is not installed. A `-DCMAKE_CXX_FLAGS=-g` build has the same code with line tables.
- `FASTMM_ALIGN_CODE` (default ON, gcc only) aligns functions to 64 bytes and loops and jump targets to 32 bytes on the fastmm targets. Without it an edit that executes nothing in a benchmark moved `BM_EngineStep_Sim` and `BM_TickToOrder_Sim` by 3 to 5 %; the measurement is in `bench/README.md`, "Code alignment". What remains is the difference between two processes of one binary (2 to 5 %), so compare a small change over several interleaved processes per side.
- `scripts/build-pgo.sh` builds `release-native` with gcc (or `--compiler clang`) PGO, trained on the hot-path benchmarks, a one-day synthetic backtest and 20 s of `scripts/bench-e2e.sh`; `--bolt` then instruments and rewrites `fastmm-live`, `fastmm-sim-itch` and three benchmarks with `llvm-bolt` (instrumentation mode, so no LBR is needed). No shipped build uses it: an identical copy of the code, profiled again, came out 7 % slower on the tick.
- `bench/ci_budget.toml` holds time budgets and counter floors, set from the measurement on the reference machine named in the file. `python3 tools/check_budgets.py bench/results/latest` exits 1 when the fastest repetition of a benchmark exceeds its budget by more than 10 %, when a benchmark reported an error, or when a median counter is below its `[min_counters]` floor; it compares the fastest repetition because interference only makes a benchmark slower. Benchmarks missing from the results are reported without failing. CI runs it over a subset of the benchmarks on a hosted runner with `--slack 2`: the runner's hardware is slower and its load unknown, so that job catches errors, counter floors and order-of-magnitude regressions, and the 10 % gate stays with whoever runs `scripts/bench.sh` on the reference machine. `tools/bench_compare.py` diffs two result directories.

## End to end over veth

`scripts/bench-e2e.sh` runs `fastmm-sim-itch` and `fastmm-live` as processes in two network namespaces joined by a veth pair: ITCH over MoldUDP64 multicast (lines A and B), GLIMPSE, re-requests and OUCH 5.0 orders cross it. BasicMM trades on the `nasdaq_itch` venue with `order_entry = "sim_ouch"`. Every order that market data triggered carries the MoldUDP64 sequence number of the first message of its receive batch in its ClOrdID; the simulator measures wire to wire with its own TSC, from right before the `sendmmsg` that first sent that datagram to right after the read that returned the order. `fastmm-live` measures the other rows: the kernel receive timestamp to T0 on the network thread, the engine's intervals T0 to T5 ([Status file](../reference/status-file.md#latency-intervals)), and T0 to the return of the OUCH write. The network thread writes all orders it drains from the outbound ring with one `write` (SoupBinTCP headers and OUCH messages together), and every order of the drain gets that write's return as its stamp. With `spin_mode = "busy"` the engine does not write the network thread's eventfd; the network thread sees the wake flag on its next loop iteration. The script reads the simulator's `--summary-json` and `fastmm-top --json` and prints p50, p99 and p99.9 per run. veth has no NIC timestamps, no zero-copy and no NAPI busy polling without XDP, so the numbers compare configurations on one machine; `bench/README.md` names the backend, spin mode and pinning of each table.

On veth the `write` runs the simulator's TCP receive path inside the system call (8 to 12 µs at p50 under WSL2). An `IORING_OP_SEND` through io_uring costs the same, since `io_uring_enter` performs the send inline. With an SQPOLL thread the send call returns in 0.3 µs, but the kernel thread then does the work on another core: wire to wire did not improve, and an unpinned SQPOLL thread made it five times slower. Neither was kept (`bench/README.md`).

## Caveats

The results in this repository were measured under WSL2 (Linux 6.6) on a machine that was also compiling and running other work. Nothing about the clock is controlled: WSL2 exposes no cpufreq governor or boost interface, there is no `isolcpus`, and ASLR is on (Google Benchmark says so on every run). The hypervisor and the other processes add scheduling jitter to every run.

A single wall-clock figure from this machine is an upper bound. `bench/README.md` publishes, for every row, the spread over all repetitions of all rounds and the CPU time beside the wall time, and the per-operation p50 where the benchmark records one. A row whose CPU time is far below its wall time, or whose spread is tens of percent, was measured while something else had the core; read its p50 and its CPU column, or re-run it. p99 counters include the host's stalls and are this machine's tail, not the code's.
