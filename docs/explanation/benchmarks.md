# Benchmarks

Results: [`bench/README.md`](../../bench/README.md), generated by `scripts/bench.sh`; its end-to-end section comes from `scripts/bench-e2e.sh`.

## Method

- `scripts/bench.sh --preset release-native --cpu 2` pins each benchmark to one core (`taskset` plus `sched_setaffinity` in the bench main), runs 5 repetitions and reports the median.
- `BM_TickToOrder_Sim` and the reactor benchmarks also record each round in a `LogLinearHistogram` and export `p50`/`p99` counters; for `BM_TickToOrder_Sim` they cover the ticks that sent orders. Tables give the median of 5 repetitions unless a figure is marked p50.
- `BM_TickToOrder_Sim` measures the engine only: a book delta into the feed, `Engine::step()`, and the orders serialised into `SimTransport`. TLS, JSON decoding and the network are outside it.
- Between timed ticks the rig runs the simulated venue and delivers acks, untimed, until no order is in flight and both quotes rest at the venue. The quote manager does not touch a pending order, so a tick that finds one sends nothing. Each timed tick moves the book by two ticks and sends one cancel per side. The benchmark reports `order_events_pct`, the share of ticks that sent orders, and fails when it is below 50 %. The median time per iteration includes Google Benchmark's pause and resume overhead around the untimed part; the `p50`/`p99` counters do not.
- The codec benchmarks time 64 operations between two `rdtsc` readings and report the median per-operation time as `p50_ns`. A benchmark that repeats one input lets the compiler hoist work out of the loop (`BM_Ouch42_EncodeEnterOrder`); the `*_NewIds` variants change the ClOrdID every call. `BM_Ouch50_EncodeColdMap` builds a fresh `UserRefMap` before each batch, so it shows what the first orders of a session pay; run it with `MALLOC_MMAP_THRESHOLD_=65536` when comparing against a build whose tables come from `malloc`, which otherwise hands back pages already faulted in by the previous batch. `BM_ItchL2Bridge_Message_DefaultBook` uses the venue's default 2^20-order book, whose index and order arrays do not fit the caches.
- Profiles: `perf` from the distribution's `linux-tools` package works unprivileged under WSL2 (`kernel.perf_event_paranoid = 2`, user-space cycles and cache events; no LBR). Unpack it with `apt-get download` and `dpkg -x` when it is not installed. A `-DCMAKE_CXX_FLAGS=-g` build has the same code with line tables.
- `scripts/build-pgo.sh` builds `release-native` with gcc (or `--compiler clang`) PGO, trained on the hot-path benchmarks, a one-day synthetic backtest and 20 s of `scripts/bench-e2e.sh`; `--bolt` then instruments and rewrites `fastmm-live`, `fastmm-sim-itch` and three benchmarks with `llvm-bolt` (instrumentation mode, so no LBR is needed).
- `bench/ci_budget.toml` holds p50 budgets and counter floors. `python3 tools/check_budgets.py bench/results/latest` exits 1 when a median exceeds its budget by more than 25 %, a benchmark reported an error, or a median counter is below its `[min_counters]` floor. It reports benchmarks missing from the results without failing; CI does not run it. `tools/bench_compare.py` diffs two result directories.

## End to end over veth

`scripts/bench-e2e.sh` runs `fastmm-sim-itch` and `fastmm-live` as processes in two network namespaces joined by a veth pair: ITCH over MoldUDP64 multicast (lines A and B), GLIMPSE, re-requests and OUCH 5.0 orders cross it. BasicMM trades on the `nasdaq_itch` venue with `order_entry = "sim_ouch"`. Every order that market data triggered carries the MoldUDP64 sequence number of the first message of its receive batch in its ClOrdID; the simulator measures wire to wire with its own TSC, from right before the `sendmmsg` that first sent that datagram to right after the read that returned the order. `fastmm-live` measures the other rows: the kernel receive timestamp to T0 on the network thread, the engine's intervals T0 to T5 ([Status file](../reference/status-file.md#latency-intervals)), and T0 to the return of the OUCH write. The network thread writes all orders it drains from the outbound ring with one `write` (SoupBinTCP headers and OUCH messages together), and every order of the drain gets that write's return as its stamp. With `spin_mode = "busy"` the engine does not write the network thread's eventfd; the network thread sees the wake flag on its next loop iteration. The script reads the simulator's `--summary-json` and `fastmm-top --json` and prints p50, p99 and p99.9 per run. veth has no NIC timestamps, no zero-copy and no NAPI busy polling without XDP, so the numbers compare configurations on one machine; `bench/README.md` names the backend, spin mode and pinning of each table.

On veth the `write` runs the simulator's TCP receive path inside the system call (8 to 12 µs at p50 under WSL2). An `IORING_OP_SEND` through io_uring costs the same, since `io_uring_enter` performs the send inline. With an SQPOLL thread the send call returns in 0.3 µs, but the kernel thread then does the work on another core: wire to wire did not improve, and an unpinned SQPOLL thread made it five times slower. Neither was kept (`bench/README.md`).

## Caveats

The results in this repository were measured under WSL2 (Linux 6.6) with no CPU isolation. The hypervisor and other processes add scheduling jitter to every run. The median of 5 repetitions is reported with its standard deviation; p99 counters include the jitter. Pages whose numbers were measured while other builds were running give the load.
